# Critique T: M0 STOP decision across the third Linux and Windows runtime evidence

**Task node:** Plan 063 M0 / adversarial reconciliation of Exploration R and Exploration S
**Critique date:** 2026-08-13
**Evidence under review:** Linux run `31631897209` / job `94232462008` / artifact `9155455275`, and Windows run `31631897216` / job `94232461652` / artifact `9155482787`, both evaluating requested head `61b2ce9815e433de65648d0b7eed4ceec22d4a5d` through PR merge commit `cba92719adb834bb0f06fc9dea469128e7a413d8`
**Recommended classification:** **ARCHITECTURE STOP for Plan 063's custom-scheme migration.** M0 is failed and not accepted; production routing and M1-M7 remain frozen. Repairing canonical result finalization is a legitimate fixture-maintenance correction, but it is not a hard predecessor to the STOP decision and it is not the single behavior correction contemplated by the Plan. The retained complete temporary payloads and raw traces are sufficient negative evidence for STOP even though they cannot be used as passing acceptance artifacts.

## Executive decision

Exploration R reaches the better next-action classification, but states parts of its case too categorically. Exploration S correctly identifies a real and narrow app-lifetime/finalization defect, but incorrectly promotes that defect into a mandatory predecessor to a Plan-level failure decision. The governing documents make valid atomic canonical JSON a hard condition for **M0 PASS**; they do not make a successful rename a hard condition for preserving and acting on **M0 failure evidence**. The ExecPlan instead says that a failed M0 must preserve its JSON/logs/measurements and stop, while Exploration E expressly allowed a sibling diagnostic JSON or log when the fixture exits before atomic finalization. The PID-scoped temporary JSON files, retained in the same run artifacts with lifecycle and runner envelopes, perform that negative-evidence role here.

The decisive fact is not the missing rename. Two packaged observations across two operating systems report the same body-size-dependent renderer working-set slope while the renderer consumes one chunk at a time:

| Packaged mode | Renderer 64 MiB delta | Renderer 128 MiB delta | Increase | Locked maximum increase | Excess |
| --- | ---: | ---: | ---: | ---: | ---: |
| Linux | 47,464 KiB | 84,804 KiB | 37,340 KiB | 16,384 KiB | 20,956 KiB |
| Windows | 46,244 KiB | 87,080 KiB | 40,836 KiB | 16,384 KiB | 24,452 KiB |

Development Linux independently reports 47,792 KiB and 82,004 KiB, an increase of 34,212 KiB and an excess of 17,828 KiB. The initial 48 MiB 64-MiB threshold is calibratable below the absolute 64 MiB ceiling; the 64-to-128 MiB slope is explicitly not raisable. Thus even if Main's 64 MiB values were calibrated, the packaged renderer failure remains. The same artifacts also report `requestSignalAborts: 0` in development and both packaged runs and a real-plugin evaluation failure, but neither issue needs to carry the STOP decision: the replicated locked RSS-slope violation is independently sufficient.

No single presently evidenced, permissible correction addresses the packaged cancellation, RSS, and plugin results together. A finalization correction changes none of them. A plugin build/preparation correction changes only plugin evaluation. A cancellation correction is permissible only if it fixes a demonstrated wiring defect without substituting an explicit renderer `reader.cancel()`, a second manual signal, or a relaxed invariant; no such common cause for the RSS and plugin failures is evidenced. An RSS correction is permissible only for a demonstrated measurement defect while retaining the below-64-MiB absolute cap, the at-most-16-MiB slope, and raw traces; no such defect explains the repeated cross-platform slope. Bundling several unrelated changes as “one correction” would evade, rather than satisfy, the Plan's one-evidence-based-correction boundary.

## What Exploration R gets right

1. **It distinguishes acceptance from diagnostic use.** R does not promote a temp payload to PASS. It says both canonical files are absent, both temp payloads say `passed:false`, and the runner did not execute its normal final validation. That is the correct starting point.
2. **It attributes the missing canonical result to a separate finalization defect.** Destroying both windows before awaiting `writeResult()` leaves Electron free to terminate while the temporary write or rename is in flight. Linux development stops at temporary-write start, Linux packaged at rename start, and Windows packaged at temporary-write start. This explains the code-0/no-canonical-result shape without explaining any recorded behavior failure.
3. **It uses raw measurements rather than the grouped assertion labels.** The fixture's grouped `try/catch` incorrectly marks all three 64 MiB assertions false after the Main bound throws and marks both 128 MiB assertions false after the renderer bound throws. R correctly separates the raw truth: byte count/digest and renderer 64 MiB passed; Main 128 MiB passed; Main 64 MiB is a calibration candidate; renderer 128 MiB fails the locked slope.
4. **It identifies independent failure domains.** Development resource-root construction, packaged plugin preparation, assertion reporting, finalization lifetime, incoming request-signal behavior, and renderer RSS are not one defect. Fixing the evident fixture defects does not automatically cure the packaged renderer slope.
5. **It reads the STOP clauses conjunctively.** Plan 063 says to stop if packaged custom protocols cannot provide cancellation with bounded memory and separately says a second failure after a reasonable correction is a STOP. The latter is an additional condition, not language requiring a cosmetic or irrelevant correction before the direct packaged-feasibility STOP can be applied.

## What Exploration R overstates or leaves uncertain

1. **“No single concrete fixture correction can make this gate pass” is stronger than the evidence proves.** The defensible formulation is: no *presently evidenced permissible* single correction accounts for all decisive failures. Runtime evidence cannot prove that no future supported-API change could ever affect more than one symptom. This distinction does not alter the recommendation because the Plan allows correction only when evidence identifies the defect; it does not authorize speculative rescue work.
2. **The cancellation verdict should not be the sole architectural basis.** The top-level M0 bullet says renderer cancellation must invoke the returned response stream's `cancel()`, and that occurred exactly once; upstream also closed and active requests returned to zero. Elsewhere Plan 063 requires renderer abort to cancel the handler's undici request, the ExecPlan requires every committed assertion true, and Exploration E expressly froze `Request.signal` abortion as part of the evidence contract. Therefore `requestSignalAborts: 0` is unquestionably a committed gate failure. What remains uncertain is whether the exact incoming-`Request.signal` observation is the only valid implementation of the higher-level cancellation outcome. R calls it architecture-decisive without acknowledging that semantic tension. The RSS slope removes any need to resolve that tension for the current STOP decision.
3. **The packaged plugin error is not evidence that CSP or custom-scheme fetch is inherently broken.** `customSchemeModuleHits: 5`, a custom-scheme stack URL, and `ReferenceError: process is not defined` show that fetching and evaluation began. Unreplaced `process.env.NODE_ENV` in a browser bundle is strong evidence of a preparation/build-shape defect. R ultimately calls it correctable, but its mode table's phrasing that real-plugin activation “fails under the required CSP/custom-scheme shape” risks conflating an invalid fixture bundle with a scheme/CSP capability failure.
4. **The temporary payloads are not equivalent to canonical failed results.** R generally preserves this caveat, but saying the runner validator was “applied” can sound stronger than it is: `validateM0Result` is a success validator that requires `passed:true`, and grouped failed assertions omit details it requires. Its rejection confirms non-acceptance and raw invariant failures, not canonical runner completion. The negative decision must rest on the raw counters/traces and artifact identity, not on pretending the normal runner path completed.
5. **The synthetic merge revision remains a qualification.** The evidence is exact for the PR merge ref, not a head-only checkout. Nothing supplied indicates M0-relevant merge drift, but the STOP record should retain that scope.

## What Exploration S gets right

1. **It identifies a concrete, falsifiable lifecycle defect.** The complete PID-scoped temp file, last lifecycle checkpoint, code-0 settlement shortly after the last windows are destroyed, and absence of fatal records strongly support premature default last-window exit. An explicit fixture-owned lifetime guard through atomic persistence is narrower and safer than a sleep.
2. **It refuses to call code 0, a parseable temp file, or partial subtest success an M0 pass.** Its production-freeze and no-gate-weakening constraints are correct.
3. **It preserves the actual negative behavior evidence.** S reports `requestSignalAborts: 0`, the locked Windows renderer slope excess, and `process is not defined` rather than hiding them behind the finalization defect.
4. **It is appropriately cautious about what Windows lifecycle checkpoints directly prove.** There is no recorded `window-all-closed`, `before-quit`, or filesystem-write completion event, so the precise last-window mechanism remains a strong inference, not an observed event.

## What Exploration S gets wrong or overstates

1. **It treats successful canonical rename as a hard predecessor to declaring architecture failure.** The Plans impose atomic canonical JSON plus every assertion true on PASS. Their failure path asks for preserved JSON/logs/measurements and STOP; it does not say negative facts are unusable until rename. Exploration E explicitly anticipated pre-atomic exit and allowed a sibling diagnostic JSON or log without synthesized passes. The retained temp JSON is PID-bound, parseable after process exit, associated with exact runner/lifecycle envelopes, and includes the raw traces and counters needed for the decisive failure. Canonical rename would improve the runner contract but would not change those facts.
2. **It selects a correction that does not account for the failed behavior.** Exploration E's transition was ONE-CORRECTION only for a concrete fixture defect that explains a behavior failure; otherwise ARCHITECTURE-STOP. The app-lifetime fix explains only why the runner saw `ENOENT`. It cannot affect already-completed renderer transfer samples, cancellation counters, or module evaluation. Calling it the authorized next action confuses result delivery with the feasibility question the evidence-preservation rerun was created to answer.
3. **It creates an extra rerun/correction stage not granted by the decision boundary.** S proposes lifecycle correction and rerun, followed by a possible separately authorized behavior correction. The prior evidence-preservation work already did not consume the behavior correction. A no-new-information finalization rerun followed by another correction would turn the bounded transition `preserve evidence -> one justified correction or STOP` into `preserve evidence -> finalization correction -> behavior correction -> decide`, despite the raw evidence already satisfying the diagnostic purpose.
4. **Its Windows-node modesty does not justify the global next action.** A single node can properly avoid claiming Linux facts it did not inspect, but the Plan-level decision must reconcile all retained runs. Linux packaged and Windows packaged independently reproduce the locked renderer slope, while Linux development does too. Once those records are considered together, waiting for a Windows canonical rename has no architectural information value.
5. **It understates the plugin attribution already available.** Exact `realPluginHits`/dependency split is absent from the result contract, but the `process` exception and prepared bundle content are enough to classify the immediate plugin symptom as a likely fixture/build-preparation defect rather than an unknown need for Node in the renderer. That still does not provide a correction for RSS or cancellation.
6. **The proposed `window-all-closed` handler is not proven to be the only or exact repair.** It is a reasonable narrow candidate, but moving persistence before last-window destruction or otherwise holding app lifetime could also repair finalization. The critique need not select among them because implementation is out of scope and none is a predecessor to STOP.

## Does temporary complete failed JSON plus raw traces satisfy STOP evidence?

**Yes, for this negative decision; no, for M0 acceptance.** The distinction is exact:

| Use | Temp JSON plus trace status | Reason |
| --- | --- | --- |
| Declare M0 PASS | **Insufficient** | The ExecPlan requires development and packaged modes to produce valid atomic result JSON with every named assertion true, and the runner must observe the intended exit/result contract. |
| Declare the run failed/not accepted | **Sufficient** | Canonical files are absent, direct runners exited code 0 contrary to the intended explicit pass/fail exit, and complete payloads themselves record `passed:false`. Any one of those blocks PASS. |
| Diagnose a specific behavior failure | **Sufficient where raw fields are complete and internally attributable** | Artifact identity, mode/platform/version, PID-scoped temp name, lifecycle, raw 25 ms samples, and counters tie the observations to the exact packaged executions. Grouped assertion labels are not relied upon for the RSS calculation. |
| Apply Plan 063 STOP | **Sufficient for the replicated locked RSS slope** | The failure-recovery rule requires preserved JSON/log/measurements, not a successful rename; Exploration E expressly allows sibling diagnostics on pre-atomic exit. Linux packaged, Windows packaged, and Linux development independently exceed the non-calibratable 16 MiB slope. |

The conclusion would be weaker if the temp files were truncated, stale, mode-mismatched, lacked raw samples, or could not be tied to the launched artifact. The handoffs report the opposite: the files parse completely, carry the expected current PIDs/modes and full result shape, reside in always-retained artifacts with launch hashes and lifecycle envelopes, and agree across platforms. A canonical rename would establish normal runner completion and protect future PASS claims; it would not make the existing negative samples more negative.

## Is canonical rename a hard predecessor to declaring failure?

**No.** It is a hard predecessor to declaring the fixture run normally completed and to declaring M0 PASS. It is also a real idempotence/runner-contract defect worth recording. But a failure gate is intentionally fail-closed: absence of canonical output already prevents acceptance, and preserved complete diagnostic evidence may establish why. Requiring the failed application to finish its success-oriented atomic publication sequence before its measurements can trigger STOP would invert that fail-closed design and contradict the explicit sibling-diagnostic allowance.

The rename correction may be made later as isolated fixture maintenance if Plan ownership wants durable failed-result ergonomics or a reusable Plan B probe. It must not be described as a correction to cancellation, memory, plugin behavior, or the Plan 063 architecture verdict, and a rerun after only that change must be expected to write the same `passed:false` facts and exit nonzero.

## Can one permissible correction rescue the decisive packaged evidence?

**No single correction is currently justified that preserves every truth condition and addresses all three domains.** The correction map is:

| Candidate | What it could fix | What it cannot fix | Plan disposition |
| --- | --- | --- | --- |
| Hold app lifetime through temp write and rename | Canonical result/exit contract | Cancellation, renderer RSS, plugin evaluation | Permissible fixture maintenance; irrelevant to feasibility verdict. |
| Correct development resource root | Linux development plugin fetch | Packaged plugin, cancellation, RSS | Permissible but development-only and non-decisive. |
| Apply the browser build's legitimate compile-time environment replacement to the real prepared plugin | `process is not defined` while retaining the real bundle shape | Cancellation and RSS | Potentially permissible after review; cannot rescue conjunctive M0 alone. |
| Split grouped assertion catches and persist plugin counters | Reporting precision | Raw failed counters/traces or actual behavior | Permissible observability correction; cannot turn failure into pass. |
| Raise 48 MiB Main threshold below the absolute 64 MiB cap | Main 64 MiB assertion only | Renderer 128 MiB slope, cancellation, plugin | The one calibration contemplated by the Plan, but insufficient. |
| Raise/average away the 16 MiB slope, discard transient peaks, or accept body-proportional growth | Would relabel RSS failure | Violates the locked canary | Forbidden weakening. |
| Accept response `cancel()`/upstream close without incoming request-signal abort, add explicit renderer `reader.cancel()`, or add a second manual signal only for the test | Would relabel or manufacture the missing counter | Does not prove the frozen end-to-end truth condition; does not fix RSS/plugin | Forbidden by Exploration E unless a concrete production-equivalent wiring defect is first demonstrated; none is shown. |
| Replace the real plugin with a toy module, expose Node globals, broaden CSP/privileges/session access, or use HTTP(S) fallback | Could bypass plugin symptom | Violates M0 security/representativeness and does not fix RSS/cancellation | Forbidden weakening. |

A hypothetical supported-API implementation change might later be proposed under a new plan, but it is not an evidenced fixture correction under the present decision boundary. The current evidence therefore selects STOP, not speculative rescue.

## Explicit uncertainties that do not change the classification

- The critique relies on the artifact facts, hashes, fields, and sample values reported in Explorations R and S; it did not independently download the expiring CI artifacts. The two handoffs are internally consistent and identify exact run/job/artifact authority.
- Neither runner read canonical result JSON. Linux packaged reached rename start; Windows packaged did not record temporary-write completion. Post-run artifact parsing proves complete JSON bytes were retained, but does not independently prove `writeFile` promise resolution or a durable atomic rename.
- The workflows evaluated a synthesized PR merge commit rather than a head-only checkout. No supplied evidence identifies M0-relevant merge drift.
- The exact Windows/Linux RSS samplers observe process working set at roughly 25 ms cadence. They can miss peaks, not invent the broad body-correlated increases shown in all three traces. No matched control transfer or reordered 128-before-64 run is supplied. That leaves allocator/JIT attribution uncertain, but the M0 canary intentionally measures the packaged process as experienced, and the repeated increase already violates its locked acceptance condition.
- Response cancellation invoked the returned body's `cancel()` once, closed upstream once, stopped chunk growth, and returned active requests to zero even though the incoming protocol `Request.signal` did not abort. Whether Electron should expose both signals is a product-semantics question. It remains a committed validator failure, but STOP does not depend on resolving it.
- Exact packaged `realPluginHits` and dependency-hit counts were not persisted. Five custom-scheme module hits and the custom-scheme stack location prove substantial routing progress, not exact route distribution. The immediate `process` failure is likely preparation-related, but a corrected bundle was not run.
- The last-window explanation is strongly supported but not directly observed through Electron quit-event checkpoints. A lifecycle fix could confirm it; such confirmation would not alter the recorded behavior payloads.
