## Why this matters

The packaged macOS arm64 app is **1.0 GB** uncompressed (`release/mac-arm64/Cradle.app`)
and ships ~300–400 MB DMGs. Three downloadable artifacts account for ~600 MB of that:

| Payload | Size in .app | How it ships today |
| --- | --- | --- |
| `@anthropic-ai/claude-agent-sdk-darwin-arm64/claude` | 302 MB | optional dep of `@anthropic-ai/claude-agent-sdk`, kept as external in the deployed server `node_modules` |
| `codex-app-server` + `codex-code-mode-host` | 171 + 55 MB | `sync-codex-runtime.mjs` pulls GitHub release assets at build time; `afterPack` copies them into `Resources/` |
| `@arcships/light-ocr-model-ppocrv6-small` | 70 MB | runtime dep of `@arcships/light-ocr`, deployed into server `node_modules` |

Everything else is legitimately bundled: Electron framework (222 MB), `app.asar`
(68 MB), server `dist` + plugins (30 MB), synchronous native deps
(better-sqlite3, node-pty, sharp, `@node-rs/jieba`, `@ff-labs/fff-node`, ~40 MB),
`relayd` (14 MB — the remote-connectivity bootstrap, spawned by Electron main
before the server exists; downloading the download channel would be circular),
cli/drizzle/skills/mac-bridge (~5 MB).

After this plan the .app drops to roughly **400 MB** and every heavy payload
arrives once per user through the same reviewed, resumable, checksum-pinned
pipeline OpenCode and Chronicle already use.

## Current state

### The managed-download pattern already exists end to end

- `packages/download-center` owns the host-agnostic HTTPS runner:
  `DownloadRequest` carries stable `owner` identity, `sources[]`, `integrity`
  (`sha256`/`sha512`), `maxBytes`; `DownloadedArtifact.filePath` is a
  host-internal capability released after promotion. See
  `packages/download-center/src/contract.ts`.
- `apps/server/src/modules/download-center` owns durable task state, queueing,
  resume, redacted task views, and SSE. `execute`/`retry`/`release` are
  host-internal; public routes are read/cancel only.
- `apps/server/src/modules/managed-resources` owns the declaration catalog and
  `install`/`update`/`uninstall` dispatch on exact
  `(namespace, resourceType, resourceId)` keys. Command routes never accept a
  URL, checksum, version, archive name, or path.
- `apps/web/src/features/managed-resources` renders the generic Resources page
  and joins Download Center tasks by exact owner identity.
- `apps/server/src/modules/chat-runtime-providers/opencode/` is the complete
  binary-runtime reference: `runtime-release.ts` + checked-in
  `opencode-runtime-manifest.json` (per-target `assetName`/`format`/`sizeBytes`/`sha256`),
  `runtime-installation.ts` (immutable `versions/<v>/`, atomic `current.json`
  pointer, `staging/`, safe zip/tar extraction, install-flight lock, boot
  cleanup), `managed-resource-adapter.ts`, and an executable precedence of
  operator override → Cradle-managed → PATH → `*_runtime_not_installed`.
- `apps/server/src/modules/chronicle/managed-resource-adapter.ts` already does
  the same for model resources, so a non-runtime `kind: 'model'` precedent
  exists too.

### Codex runtime is bundled, not managed

`apps/desktop/scripts/sync-codex-runtime.mjs` knows every supported target
(`darwin-x64/arm64`, `linux-x64/arm64` musl, `win32-x64/arm64`) and downloads
three assets per target from `openai/codex` GitHub releases into
`apps/desktop/resources/codex/<platform>-<arch>/` — a dev/build cache that is
never itself packaged.

`electron-builder.mjs` `afterPack` calls `copyCodexRuntimeToPackagedResources`,
which copies only `codex-app-server` + `codex-code-mode-host` for the built
target into `Resources/`; the 210 MB `codex` CLI is **not** shipped (it is only
needed for `codex app-server generate-ts` protocol generation at dev time).

`codex-app-server` resolves `codex-code-mode-host` itself — the binary contains
`enable \`features.code_mode_host\` and install \`codex-code-mode-host\``, and it
looks for the sibling executable. Both must land in the same managed version
directory.

Desktop injects the bundled path into the server:
`apps/desktop/src/main/server-process.ts:933-971`
(`resolveDesktopCodexAppServerPath`) hard-fails packaged builds when
`Resources/codex-app-server` is missing, then exports
`CRADLE_CODEX_APP_SERVER_PATH` in `serverEnv` (line ~567).

Server-side resolution already has the right tail
(`apps/server/src/modules/chat-runtime-providers/codex/app-server/client.ts:503-535`):
`CRADLE_CODEX_APP_SERVER_PATH` → PATH `codex-app-server` → `codex app-server`
CLI fallback. The managed slot belongs between the env override and PATH.

`<data>/runtimes/codex-app-server` already exists as the Codex runtime home
(`app-server/runtime-home.ts`); the managed install root must not collide with
session data, so it lives in a `managed/` subdirectory.

### Claude Code binary rides in through an npm optional dep

`@anthropic-ai/claude-agent-sdk@0.3.261` (declared in `apps/server/package.json`)
is pure JS (~4 MB). The `claude` executable ships as per-platform optional
packages `@anthropic-ai/claude-agent-sdk-<platform>-<arch>@<sdkVersion>` whose
entire payload is the binary; `sdk.mjs` resolves them relative to its own URL.

`Options.pathToClaudeCodeExecutable` is a supported override. Every Cradle
`query()` call site builds options through one seam —
`buildClaudeQueryOptions` in
`apps/server/src/modules/chat-runtime-providers/claude-agent/input-projector.ts`
(provider turns, presentation, quick-question, title generation) — except
`account-diagnostics.ts`, which builds its own `Options`. Both seams consume one
new resolver.

`<data>/runtimes/claude-agent` already exists as `CLAUDE_CONFIG_DIR`
(`runtime-context.ts:62-90`); the managed binary root lives in a `managed/`
subdirectory so it never mixes with config/transcript state.

### OCR model is a 70 MB npm dependency

`apps/server/src/modules/image-ocr/service.ts` calls
`createEngine()` from `@arcships/light-ocr`, which resolves its model bundle
from the `@arcships/light-ocr-model-ppocrv6-small` package (a plain `bundle/`
directory, pinned at `0.3.4` by light-ocr `0.5.7`). `createEngine` already
accepts `bundlePath`, so the bundle can live anywhere on disk. The engine is
only constructed lazily on the first `POST /image-ocr/recognize` call — a
perfect on-demand boundary.

### Server packaging has an explicit externals seam

`apps/server/scripts/prepare-desktop-runtime.mjs` runs `pnpm deploy --prod`
then prunes the deployed `node_modules` to the transitive closure of
`desktop-runtime.externals.json`. Adding a scoped exclude list
(`@anthropic-ai/claude-agent-sdk-*`, `@arcships/light-ocr-model-*`) at the
prune step drops both heavy payloads without touching the externals list
itself — the JS SDK and the OCR runtime stay external and keep working in dev
and standalone installs where their optional deps resolve normally.

### Update flow already exists

`.github/workflows/update-chat-runtime-sdks.yml` bumps the Claude SDK, the
Codex runtime, and Kimi in one reviewed PR (see the
`cradle-chat-runtime-sdk-update` skill). Manifest regeneration slots into that
same workflow so checked-in manifests can never drift from the SDK/protocol
versions they claim to match.

## Target interface and state

### Shared versioned-installation primitive

Extract the generic machinery from
`chat-runtime-providers/opencode/runtime-installation.ts` into
`packages/download-center` (it is host-agnostic, owns no DB/IPC/routes — inside
that package's stated boundary). Suggested exports:

- `VersionedInstallation` — owns `rootDir/{versions/<version>/,staging/,current.json}`:
  immutable version dirs, `installation.json` inside each version dir, atomic
  `current.json` pointer write (tmp + fsync + rename), boot cleanup that wipes
  `staging/` and non-current versions, install-flight serialization, and
  uninstall that refuses while a provided `inUse` callback says the active path
  is still leased.
- Safe archive helpers — the existing two-pass zip/tar extraction:
  entry-path validation (no absolute paths, no `..`, no NUL), entry-type
  allowlist (directories + regular files only, no symlinks/devices), and an
  expected-file-set matcher so each owner declares exactly which files an
  archive may contain.

Owners keep: manifest schema + sync script, target/platform resolution,
executable precedence, version probing, health status, managed-resource
adapter, and `prepareManagedPathForRemoval`-style lease draining. Do **not**
build a generic "runtime installer" HTTP surface; commands still dispatch
through Managed Resources on exact keys.

Refactor OpenCode onto the primitive first (M0). Its existing test suite is the
parity harness — `runtime-installation.test.ts` must keep passing with the
shared implementation.

### Codex (`chat-runtime-providers/codex/`)

- New checked-in `codex-runtime-manifest.json` + `runtime-release.ts`, generated
  by `apps/server/scripts/sync-codex-runtime-manifest.mjs` (mirror
  `sync-opencode-runtime-manifest.mjs`). `releaseTag` is pinned to the release
  the vendored `app-server-protocol/` was generated from — bumping the manifest
  without regenerating protocol bindings is a review blocker, enforced by the
  sync script's `--check` mode comparing against the vendored MANIFEST.
- Per-target manifest entries carry both assets:
  `{ appServerAsset: { name, sizeBytes, sha256 }, codeModeHostAsset: { name, sizeBytes, sha256 } }`
  using the GitHub release `digest` field, same as OpenCode.
- Install root: `<data>/runtimes/codex-app-server/managed/`. Each
  `versions/<tag>/` contains both executables side by side so the app-server's
  own sibling resolution for `codex-code-mode-host` keeps working.
- Executable precedence (`resolveCodexAppServerLaunch`):
  1. `appServerPath` arg / `CRADLE_CODEX_APP_SERVER_PATH` (operator, external)
  2. Cradle-managed `current.json` pointer
  3. PATH `codex-app-server` (external)
  4. `codex` CLI fallback (external, unchanged)
- Desktop: `resolveDesktopCodexAppServerPath` stops resolving packaged
  resources entirely — it only honors an explicit
  `CRADLE_CODEX_APP_SERVER_PATH` override, in dev and prod alike, so dev
  exercises the same managed/PATH/CLI resolution chain as prod.
  `electron-builder.mjs` drops `copyCodexRuntimeToPackagedResources` from
  `afterPack`.
- `sync-codex-runtime.mjs` stays as the dev/protocol-generation cache tool and
  gains `--managed`, which also writes the managed-install layout
  (`versions/<v>/bin`, `installation.json`, `current.json`) into
  `resolveCodexAppServerHome()/managed`, so dev can use the same resolution
  path as prod.

### Claude (`chat-runtime-providers/claude-agent/`)

- New `claude-code-runtime-manifest.json` + `runtime-release.ts`, generated by
  `apps/server/scripts/sync-claude-code-runtime-manifest.mjs`. The script reads
  the installed `@anthropic-ai/claude-agent-sdk/package.json`
  `optionalDependencies` (never a hardcoded platform list), resolves each
  `@anthropic-ai/claude-agent-sdk-<platform>` tarball from the npm registry
  packument, and records `{ tarball, sha512 (from dist.integrity), unpackedSize }`
  per target. `maxBytes` uses a fixed generous bound (~500 MB) because the
  packument does not publish compressed size; integrity comes from the pinned
  sha512.
- Optional secondary source (e.g. an npmmirror tarball URL) may be recorded as
  `sources[1]` — Download Center already fails over across `sources[]`.
- Install root: `<data>/runtimes/claude-agent/managed/`. Extraction accepts a
  single `claude`/`claude.exe` executable entry from the npm tarball.
- Executable precedence:
  1. `CRADLE_CLAUDE_CODE_PATH` operator override (external)
  2. Cradle-managed `current.json` pointer
  3. SDK-bundled platform package (dev workspaces and standalone server
     installs where pnpm/npm installed optional deps — keep this resolution so
     `pnpm dev` and `npx @cradle/server` keep working with zero downloads)
  4. PATH `claude` (external)
  5. Missing → `claude_agent_runtime_not_installed` before any spawn
- Injection seam: `buildClaudeQueryOptions` sets
  `pathToClaudeCodeExecutable` whenever the resolver returns a concrete path
  (steps 1, 2, 4). Step 3 leaves it unset so the SDK self-resolves. 
  `account-diagnostics.ts` consumes the same resolver.
- Uninstall/update gating mirrors OpenCode: active `query()` sessions hold the
  absolute versioned path; a new `prepareManagedPathForRemoval` hook refuses
  removal while sessions run.
- Packaging: `desktop-runtime.externals.json` keeps
  `@anthropic-ai/claude-agent-sdk`; `prepare-desktop-runtime.mjs` gains a
  `prunePackages` glob list (`@anthropic-ai/claude-agent-sdk-*`) applied after
  reachability pruning, recorded in `desktop-runtime.json`.

### OCR model (`modules/image-ocr/`)

- New `model-release.ts` + `ppocrv6-model-manifest.json`, generated by
  `scripts/sync-light-ocr-model-manifest.mjs`, which reads the model package
  version pinned by the installed `@arcships/light-ocr` dependency tree and
  resolves its npm tarball the same way (sha512 integrity, generous `maxBytes`).
- Install root: `<data>/runtimes/image-ocr/ppocrv6-small/` with the same
  versioned layout. Extraction allows only the `bundle/` subtree.
- `service.ts` `getEngine()` resolves `bundlePath` through the installation

  (dev/standalone) → else `image_ocr_model_not_installed`.
- Packaging: same `prunePackages` mechanism drops `@arcships/light-ocr-model-*`.

### Install UX and continuity

- Codex is `required: true` — it backs the default runtime — so onboarding
  must present its install before first use (see the runtime-setup step demo
  in `apps/web/src/features/onboarding/runtime-setup-step-view.*`; Claude is
  the optional row there). Outside onboarding, Codex and OCR behave like
  OpenCode: explicit install from Resources, and a stable `*_not_installed`
  `AppError` before spawn/recognize. This is a behavior change for Codex,
  which previously worked out of the box — the migration note goes in release
  notes, and the not-installed error must surface a usable path forward in
  chat (the provider error already flows to the UI; the web layer maps
  `*_not_installed` codes to a Resources deep link — verify this join exists,
  otherwise add the mapping in the generic chat error surface, not a
  codex-only branch).
- Claude is `required: false` for this migration even though it backs a
  primary runtime — the onboarding step treats it as optional alongside
  OpenCode. First-use flow: the composer/provider surface reacts to
  `claude_agent_runtime_not_installed` by offering an install action that
  dispatches the existing managed-resource `install` command and follows
  progress through Download Center events. No parallel download UI. Automatic
  background install on first launch is explicitly out of scope for this plan —
  it is a product decision layered on the same dispatch later.
- Cradle-managed binaries disable vendor auto-update channels where they exist
  (OpenCode already sets `OPENCODE_DISABLE_AUTOUPDATE=1` on managed processes
  only). Claude Code auto-update does not apply to the raw binary + SDK launch
  path; verify `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` coverage stays as-is.

## STOP conditions

- `codex-code-mode-host` turns out to be resolved from PATH only (not sibling):
  adjust the version-dir layout before implementing; do not guess.
- `pathToClaudeCodeExecutable` does not cover some query mode Cradle uses
  (check `sdk.mjs` handling for every Options field Cradle sets): stop and
  reassess rather than patching the SDK.
- The npm platform tarballs for Claude or the OCR model are not publicly
  fetchable without auth, or integrity metadata is absent: stop; the fallback
  channel is Anthropic's official `claude-code-releases` distribution / the
  OCR vendor's own artifact host, which changes the manifest shape.
- Managed Resources or Download Center needs a contract change to express any
  of this: stop and redesign the contract first instead of leaking
  owner-internal fields (URL, headers, paths) into public projections.

## Open questions

- Should Codex auto-install on first use (preserving today's "it just works"
  continuity for upgraders) or require an explicit Resources click like
  OpenCode? Plan defaults to explicit; auto-install is a later product decision
  on the same dispatch.
- Secondary download sources (npm mirror for Claude/OCR, any Codex mirror for
  CN reachability): manifest `sources[]` supports them, but which mirrors are
  acceptable is a supply-chain decision, not a technical one.
