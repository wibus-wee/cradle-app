# Codex Runtime Provider

Owns the Codex app-server runtime adapter for Chat Runtime. This directory translates between Cradle `UIMessage` state and the Codex JSON-RPC app-server protocol.
Codex tool identity and the `{ identifier, apiName, args, result }` envelope are owned by `tools/`; this provider only maps app-server protocol items into that stable contract.
Selected chat Skills arrive as Cradle-owned `data-cradle-skill` message parts. The provider reads them and projects them into Codex app-server `UserInput` skill items without writing to any skills namespace.
Codex thread display titles are read from app-server `thread/start`/`thread/resume` responses, `thread/name/updated` notifications, and final `thread/read` metadata, then reported through Chat Runtime's title callback. Provider metadata is normalized as `name`, then persisted `title`, then `preview`; Cradle owns the final `sessions.title` write. When a fresh Codex thread starts without a name, this provider opportunistically starts a separate ephemeral app-server title thread in the background, using Chat-owned title-generation preferences for provider target, explicit model, and thinking effort; when provider/model are unset it follows the active chat session provider/model. The generated title is written back through app-server `thread/name/set` for the main thread and reported to Chat Runtime; the title turn is not awaited by the main `turn/start` path and is not injected into the main Codex session.
Each provider target owns one warm Codex app-server host. The host is retained for 30 minutes after its last lease and routes notifications plus interactive server requests by exact Codex thread id. Active operations consume one notification at a time with pull backpressure; request-only and pinned leases do not own payload mailboxes. An early notification can wait in the pump while an in-flight binder resolves its thread id, but it is never appended to a per-thread tail. Idle unowned notifications are counted and discarded. Native process termination invalidates only that host generation, so a delayed exit cannot invalidate its replacement.
The provider process receives only provider-scoped auth and model-provider environment/config. Cradle-owned `CRADLE_CHAT_SESSION_ID`, `CRADLE_WORKSPACE_ID`, `CRADLE_WORKSPACE_PATH`, and agent context are bound on each `thread/start`/`thread/resume`/`thread/fork` through Codex `shell_environment_policy.set` (and through the Cradle MCP server config when present), so shell and MCP work keeps the correct thread context without making the process chat-scoped. Skill extra roots are a monotonic host-wide union.
Agent-scoped Codex sessions use `~/.cradle/agents/{agentId}` as thread `cwd`. The original project remains explicit through `runtimeWorkspaceRoots`, sandbox writable roots, and per-thread `CRADLE_WORKSPACE_PATH`; the provider does not change Codex's global `CODEX_HOME`, which stays under Cradle's app-server runtime data directory.
Codex auth is selected explicitly on each Cradle provider target and is backed by Cradle-owned encrypted credentials. The supported modes are ordinary OpenAI-compatible API key auth, ChatGPT Login, Codex Personal Access Token, and AWS Bedrock API Key. API-key auth stores the existing provider-kind secret and projects `CRADLE_CODEX_API_KEY`, `CODEX_API_KEY`, and `OPENAI_API_KEY` into the app-server process. ChatGPT Login stores encrypted JSON as a `chatgpt-auth` secret, calls `account/login/start` with `chatgptAuthTokens`, leaves API-key environment variables unset, and handles `account/chatgptAuthTokens/refresh` by refreshing OAuth token material back into that same secret row. Provider-target account diagnostics read Codex-native account identity, auth-required state, rate limits, reset-credit availability, and token usage without projecting auth tokens. Personal Access Token stores a `codex-personal-access-token` secret and projects it only as Codex's native `CODEX_ACCESS_TOKEN`. Bedrock stores a `codex-bedrock-api-key` secret, stores non-secret `bedrock.region` in provider config, projects `AWS_BEARER_TOKEN_BEDROCK` plus `AWS_REGION`, and writes Codex's native `amazon-bedrock` model-provider config. The resolver uses the secret row's `kind`; it does not infer auth type from token prefixes, base URLs, model names, or secret payload shape.
Existing Codex threads are resumed with `excludeTurns: true` once per host lifetime, with concurrent binds single-flighted. The durable binding stores only the native thread id, common workspace/model envelope, and latest bounded native token aggregate. Codex owns rollout history; Cradle never copies `Turn[]` into a binding and never calls `thread/turns/list` as a resume side effect. A fresh native thread does not silently replay the Cradle transcript as equivalent Codex history. Legacy snapshots are normalized through the Codex-owned checkpoint codec and written back compactly on first resume.
Goal slash commands and internal goal continuations are provider-native control messages, not chat text. A visible `/goal <objective>` command or goal metadata message sets `thread/goal/set` with an objective, and an internal Chat Runtime goal-continuation message sets `thread/goal/set` with `status: "active"` without calling `turn/start`. The provider then streams the resulting app-server notifications as the current run. During a goal handoff, live steer waits for app-server's next `turn/started` fact and uses that exact turn id; `turn/completed` clears the provider's active-turn projection so Cradle never treats an old or not-yet-published turn id as native session state. When the optional blocked-goal continuation policy is enabled, Chat Runtime resumes a blocked Codex goal through one direct `thread/goal/set` bridge call instead of creating an internal continuation run, so a blocked snapshot cannot self-schedule empty runs. User cancellation pauses an active Codex goal in the provider snapshot before interrupting the current turn so Chat Runtime does not auto-resume from stale active-goal state.
Composer bang commands in Codex runtime are provider-native shell commands, not Chat Runtime local execution. Chat Runtime calls the provider's `executeShellCommand` hook, and the provider resumes/starts the Codex thread, sends `thread/shellCommand`, waits for the matching `commandExecution` item, and returns bounded result metadata without hydrating rollout history.
Codex conversation rollback is always in place. The provider first ensures the persisted parent thread is loaded in the current host, lists the requested newest turns with app-server `thread/turns/list`, then calls `thread/revert` with the oldest targeted turn id; it never substitutes `thread/fork`, provider-session rebinding, or workspace file restoration for rollback.
Side chat remains Cradle-owned and live-only. When Chat Runtime asks for `forkRuntimeSession`, this provider loads the parent, maps it to app-server `thread/fork` with an ephemeral, turn-excluding child thread, injects a Cradle side-boundary prompt through `thread/inject_items`, and returns the forked provider thread id for the process-local side runtime session. The provider does not create a durable binding for the child; a pinned lease on the shared provider host keeps it live while the side session exists. Providers that do not expose this hook still receive Chat Runtime's Cradle transcript fallback; Codex's hook only upgrades native fidelity.
Codex app-server stream failures keep user-facing errors short: retry-limit and status failures are summarized through `CodexProviderError.data.details`, while full raw event samples, counts, and app-server error notifications stay in `data.diagnostics` for observability/debugging.
Codex app-server approval callbacks are routed through Chat Runtime pending tool approvals instead of being default-denied. The provider maps command, file-change, permission, `applyPatchApproval`, and `execCommandApproval` server requests into standardized tool chunks with `tool-approval-request`, waits for Chat Runtime's approval promise, then returns the Codex-native response shape such as `accept` / `decline` or `approved` / `denied`.

## Approval Modes

Runtime access settings preserve three distinct Codex security modes. `approval-required` uses `approvalPolicy: on-request` with `approvalsReviewer: user`; `approve-for-me` keeps the same workspace-write sandbox and on-request policy but delegates each protected action to Codex's `auto_review` reviewer; `full-access` uses `approvalPolicy: never` with the danger-full-access sandbox. The reviewer is projected on thread start/resume, every turn, and live thread settings updates. Guardian review events feed the approvals UI slot with status, risk level, and rationale.

Codex token usage notifications stay provider-owned at the protocol boundary. Fresh threads opt into raw events so `rawResponse/completed` supplies exact per-response usage and its provider timestamp; the usage projector pairs that fact with the following `thread/tokenUsage/updated` cumulative snapshot. Exact usage becomes the durable event delta, while the cumulative total remains the replay identity and `providerTotal`. Older resumed threads cannot enable raw events through `thread/resume`, so they retain the cumulative notification's `last` usage fallback. Chat Runtime owns the durable `usage_logs` write during run finalization, including cache-read and cache-write input tokens.
Codex `account/usage/read({ threadId })` is a separate provider billing read model exposed beside existing per-session Usage totals. It reports provider estimates and a token delta for reconciliation, but never enters provider-event ingestion and never creates or replaces `usage_logs` ledger rows. Active app-server hosts also expose native `server/diagnostics` process and gauge snapshots through Cradle Observability; provider-native gauge names remain JSON diagnostics rather than becoming global metric labels.
Codex UI slots are projected from the app-server capability manifest and declare their intended Cradle surfaces. Host-global catalogs/config and thread facts are hydrated once per host generation and invalidated by their owning native changes, so ordinary two-second UI polls are in-memory reads rather than a twelve-RPC fan-out. Compact Context Usage uses native `last.totalTokens` as current-window occupancy; cumulative `total` remains lifetime accounting and detailed provider sections return `null` because Codex does not expose their composition.

## Files

- `provider.ts`: Codex `ChatRuntime` facade; delegates app-server host leases, stream-turn context preparation, active-turn tracking, bounded checkpointing, and host-fact hydration, then starts/resumes app-server threads, forks ephemeral provider-native side threads, reports titles, executes provider-native operations, and streams notifications.
- `provider.test.ts`: Regression tests for Codex thread startup, provider title projection, provider config, transcript reconstruction, UI slot state projection, streaming, steering, cancellation, and diagnostics.
- `integration/live-steer-goal-handoff.integration.test.ts`: Opt-in real app-server plus `model-api-simulator` regression coverage for live steer across a goal handoff.
- `metadata.ts`: Codex runtime kind, catalog metadata, static capabilities, and app-server capability presentation projection.
- `types.ts`: Codex provider-private client, dependency, and active-turn types shared by package modules.
- `app-server/`: Codex app-server boundary: JSON-RPC client, generated capability manifest, provider-native app-server bridge, interactive server-request method helpers, host lease/resource/fingerprint helpers, ChatGPT auth/account and per-thread billing readers, native diagnostics, and model listing.
- `config/`: Runtime config projection: Codex config payloads, sandbox/access policy projection, per-session runtime context, and temporary system-prompt file creation.
- `turn/`: Single-turn orchestration helpers: active-turn registry, stream-turn context preparation, input projection, notification-to-`UIMessageChunk` mapping, stream diagnostics, stream iteration, thread lifecycle, explicit quick-question/side-boundary injection, title generation, and shell command execution.
- `projection/`: Cradle-owned bounded live/UI projections and native aggregate usage readers.
- `state/`: Codex-owned durable checkpoint codec and legacy value normalization.
- `tools/`: Codex tool identifier and app-server item payload mapper.
- `usage-event-projector.ts`: Projects native per-call usage notifications into deterministic runtime usage events before root-thread filtering.
- `usage-reconciliation.ts`: Replays only Cradle-bound root/descendant rollouts from the dedicated Cradle Codex runtime home into the same usage event identities used by the live path. A binding switches only after its complete rollout is unambiguous; the transaction writes v2 events and removes only that session's legacy summary rows.
- `usage-reconciliation-scheduler.ts`: Runs after the server is available: it prioritizes the newest 200 pending Cradle bindings, then continues in low-priority batches without blocking startup. Binding-owned reconciliation status persists completed and blocked outcomes across restarts.
- `app-server-protocol/`: Generated TypeScript bindings from `codex app-server generate-ts --experimental --out apps/server/src/modules/chat-runtime-providers/codex/app-server-protocol`. Do not edit generated files by hand.

本地资源从同一个 Codex release 同步完整 `codex` 与独立 `codex-app-server`：协议生成固定使用前者的 `codex app-server generate-ts`，Desktop 发行包只携带后者。运行时优先使用独立二进制的 stdio transport，并设置 `--session-source cli`。非 Desktop 环境按 `CRADLE_CODEX_APP_SERVER_PATH`、`PATH` 中的 `codex-app-server`、最后 `codex app-server` 的顺序解析；最后一种 fallback 仍由 Codex 报告为 VSCode session source。

## Regeneration

After regenerating `app-server-protocol/`, run `pnpm --filter @cradle/server generate:codex-app-server-capabilities` to refresh `app-server/capabilities.ts`. The capability generator derives method names and params from the generated protocol files, and keeps only Cradle-owned runtime semantics such as stream-capable methods in the generator.

Run the isolated live-steer reproduction with `CRADLE_CODEX_APP_SERVER_PATH` pointing to a synced app-server binary:

```sh
CRADLE_CODEX_APP_SERVER_INTEGRATION=1 \
pnpm --filter @cradle/server exec vitest run src/modules/chat-runtime-providers/codex/integration/live-steer-goal-handoff.integration.test.ts
```
